Follow the tutorial at: [Deploy Your Container | Web Development and Delivery](https://webdevdelivery.com/tutorials/11-deploy-your-container/).

In `Dockferfile` you need to add multi-stage 'tags' so that Docker only builds things depending on the container being built. Each stage begins with the FROM command. You use the `AS` in order to specify the container which allows it to be specified as a target.

What differentiates the dev and production builds is that they both start from 'base' instead of node:22-slim, and this is because the base stage installs from node and the other environments simply need to copy the package.json and the package-lock.json files.

The frontend stage exists only to run `npm run build` to create a static build for the EC2 instance on AWS. 

Below is what your `Dockerfile` should look like.

#### Base

```
FROM node:22-slim AS base
  

WORKDIR /app
 

# Copy the package files and install dependencies

COPY backend/package.json backend/package-lock.json ./

ENV PORT=8000

EXPOSE 8000
```

#### Development (Dev)

```
FROM base as dev

  

RUN npm ci

  

# Create uploads directory

RUN mkdir -p /app/uploads

  

# Source code is volume-mounted in development, so no COPY for src/

# This keeps the image lean and lets bind mounts handle live code

  

CMD ["npm", "run", "dev"]
```

#### Frontend 

Remember to add this between Development and Production. 

```
################### Frontend stage: builds the frontend into static files
FROM node:22-slim AS frontend

WORKDIR /frontend
COPY frontend/package.json frontend/package-lock.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build
```


#### Production

```
################### Production Stage

FROM base as production

  

ENV NODE_ENV=production

### Ignores any 'dev' dependencies

ENV npm ci --omit=dev

COPY backend/ ./

  

# Copies the static build from the frontend stage

COPY --from=frontend /backend/dist ./dist

  

# The folder for uploads when S3_BUCKET is not set. Owned by the node user,

# so the app can write to it without running as root.

RUN mkdir -p uploads && chown node:node uploads

  

USER node

CMD ["node", "server.js"]
```

Afterwards, you need to go to `compose.yaml` and add the following below 'build' with indentations. Remember to run `docker compose up -d --build` to see if it's still working.

```
services:
	app:
		build:
			context: .
			target: dev
```

### Production

Depending on what machine you're working on in the future you might have to check what format the image is being built on with `docker image inspect notes-app --format ''`. An image built for one type of machine will not run on another. To specify the specific platform for the lab computers we'll need to run:

```
docker build --platform linux/amd64 --target production -t notes-app .
```

### Configurations and Secrets

***Configurations.*** A value that changes between environments but isn't sensitive.

***Secrets.*** A value that does not change per environment and is highly sensitive such as API keys.

On AWS, there is a service called Secret Service Manager (SSM) where you can configure how to manage your secrets. To store environment variables securely and in a more convenient place, you're going to use the **Parametre Store** which is part of SSM.

```

  --query 'Parameters[].[Name,Value]' --output text
```
